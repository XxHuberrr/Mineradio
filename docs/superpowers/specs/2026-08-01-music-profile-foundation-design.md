# Mineradio 本地音乐画像与推荐模式设计

## 1. 目标

让用户先看懂自己的音乐偏好，再由用户明确开启的推荐模式改变临时播放队列。功能必须完全本地、可解释、可关闭，且不修改用户保存的任何歌单。

成功不以“算法看起来聪明”为标准。对同一用户，比较启用画像前后相同观察窗口内、推荐模式实际生效的播放：快速切歌率下降且主动收藏率增加，才说明推荐变好；样本不足时不作结论。

## 2. 范围和分期

### 第一阶段：本次贡献

- 默认关闭、完全本地的音乐画像。
- 风格、语种、年代三类可解释标签。
- 首页画像卡片与播放器控制区的同步推荐模式开关。
- 当前临时播放队列中，保护前五首尚未播放歌曲，只重排第六首及以后。
- 用户手动拖动过的队列歌曲不再被算法调整。
- 标签的“减少此类推荐”、自动恢复和简短推荐理由。
- 一键清除画像及其所有推荐影响。

### 第二阶段：明确后置

- 自动删除当前临时队列第六首及以后的低匹配歌曲。
- 仅删除 Mineradio 本机历史中从未播放过的歌曲。
- 队列少于三首时一次补充五首外部歌曲。
- 外部歌曲允许跨平台混合，但必须可合法播放、去重且不需要绕过登录、会员或版权限制。
- 可展开的完整推荐证据链和外部新歌发现。

### 永久不做

- 修改、删除、重排或写回用户保存的歌单。
- 自动收藏、自动加入歌单或自动删除用户已听过的歌曲。
- 从歌曲名、歌手名或其他非可信来源猜测元数据。
- 保存、读取或上传 Cookie、播放 URL、歌词、封面或其他账号凭证。

## 3. 数据和隐私

画像默认关闭。用户主动启用后，应用才在 Electron 用户数据目录保存本地 JSON 状态；不增加 Python 进程、独立 HTTP 服务或第三方依赖。

状态至少包含版本、启用状态、播放事件、聚合标签和用户手动降权。每条事件只保存歌曲稳定标识、有效播放时长、发生时间和可信标签维度；最多保留 500 条事件。写入使用同目录临时文件后原子重命名，读取失败或文件损坏时安全降级为空画像。

清除画像会删除事件、标签和所有手动降权，并自动关闭推荐模式。画像和推荐模式均可跨应用重启持久化；应用启动时必须清楚显示推荐模式是否已开启。

## 4. 标签规则

### 覆盖范围

所有在线音乐来源都可贡献画像。播客不进入音乐画像，本地音乐不进入第一阶段。歌曲缺失可信风格、语种或年代元数据时，该维度不产生标签，界面显示“数据不足”。

### 统一标签

各平台原始风格映射为少量统一大类，画像与队列排序只使用统一大类。原始标签可作为第二阶段完整解释的证据。语种、年代也使用统一值域。

一首歌具有多个风格、语种或年代值时，该维度的总贡献按值数量均分；未知值不参与。这样歌曲不会因平台标签数量更多而被重复放大。

### 用户纠错和恢复

用户可对任一标签选择“减少此类推荐”。标签不从画像删除，但在推荐排序中长期降权。

若近 30 天内至少五首不同歌曲在该标签上产生完播或收藏等正向行为，系统将该标签恢复到正常推荐权重，并持久保存恢复终态；窗口过期后不再自动回落。用户清除画像时同时清除该降权和恢复状态。

## 5. 播放信号与冷启动

推荐模式在至少五首不同歌曲已有有效行为后才能改变排序；此前只记录并显示“还需 N 首不同歌曲”。

初始推荐排序权重为：

- 前 15% 内的用户主动切歌：负向 50%。
- 用户主动收藏：正向 40%。
- 完播：正向 10%。

这些是待验证的排序权重，不是用户“不喜欢某首歌”的概率。系统只记录切歌位置和事实，不显示或承诺固定概率。

普通音乐播放达到总时长 80% 视为完播。长 DJ 曲目播放达到总时长 50% 视为有效长时收听。播客不参与这些音乐偏好规则。

## 6. 推荐模式行为

推荐模式可从首页画像卡片和播放器控制区切换，两个入口必须使用同一个本地状态并立即同步。

模式开启且冷启动门槛满足时：

1. 只读取当前临时播放队列，不写回原始歌单。
2. 当前播放后的前五首尚未播放歌曲保持原序。
3. 从第六首开始，按画像得分重新排序。
4. 用户手动拖动过的队列歌曲保持原位置，后续算法不调整。
5. 用户在前 15% 内主动切歌时，立即仅重排受允许调整的后半段。

关闭推荐模式后，保留当前临时队列顺序，但停止一切后续调整。推荐模式跨应用重启保持开启；清除画像时自动关闭。

第一阶段不会删歌、补歌或搜索新歌。当前队列不足六首时没有安全调整区，因此不重排。

## 7. 第二阶段的队列扩展

自动删除和补歌仅操作临时播放队列第六首及以后，绝不修改用户保存歌单。

“未听过”严格指 Mineradio 本机历史中没有播放记录，界面不得声称用户在所有平台或设备上从未听过。当前临时队列少于三首时可自动补五首跨平台候选；候选必须来自当前已连接、合法可播放的平台，且要跳过版权受限、会员受限、登录过期、无播放地址或重复歌曲。

跨平台去重分两层：优先按可靠录音版本标识去重；标识缺失时按标准化歌名和主歌手兜底。同名同歌手但明确是现场、Remix、伴奏、Acoustic 或时长明显不同的版本保留为不同录音版本。

## 8. 界面与解释

| 状态 | 界面内容 | 系统行为 |
| --- | --- | --- |
| 未启用 | 启用说明和按钮 | 不记录画像事件 |
| 学习中 | 还需 N 首不同歌曲、数据不足说明 | 记录事件，不重排 |
| 已就绪、模式关闭 | 三类标签、证据歌曲数、开启模式按钮 | 只展示画像 |
| 已就绪、模式开启 | 模式状态、标签、短推荐理由、关闭按钮 | 重排允许调整的队列后半段 |
| 标签恢复 | 标签恢复提示和原因 | 恢复该标签正常排序权重并持久保存终态 |

第一阶段的短推荐理由只解释本次排序，例如“更优先安排你近期较少跳过、且多次收藏的中文流行歌曲”。不得使用伪精确表述，例如“你有 70% 概率不喜欢”。第二阶段才增加可展开的完整证据链。

## 9. 错误处理

- 画像文件缺失、损坏或不可读：视为空画像，播放器继续正常工作。
- 用户主动点击启用、清除、标签偏好或推荐模式时，画像 API 失败必须显示反馈；后台播放/收藏画像上报可静默失败，当前播放和平台 scrobble 不受影响。
- 可信元数据缺失：保留基础播放事实，但不创建对应维度标签。
- 推荐模式错误：保持当前队列，不执行部分重排。
- 清除画像只影响画像及推荐设置，不删除 Cookie、歌单、平台历史或既有播放统计。

## 10. 验收标准

1. 新用户默认未启用，且未启用时不写入画像。
2. 画像只保存本地必要事件，不含 Cookie、播放 URL、歌词或封面。
3. 至少五首不同歌曲产生有效行为前，推荐模式不改变队列。
4. 有可信元数据的在线音乐能生成风格、语种、年代标签；缺失时显示数据不足。
5. 普通音乐和长 DJ 分别按 80% 与 50% 规则产生完播正向信号；播客不影响音乐画像。
6. 推荐模式只能调整当前临时队列第六首及以后，且不能调整用户手动拖动过的歌曲。
7. 关闭模式不还原当前队列，但停止后续调整；清除画像会关闭模式。
8. 用户保存歌单的内容与顺序在任何情况下不变。
9. 标签降权在 30 天内五首不同歌曲的正向证据后恢复到正常权重，恢复终态持久保存并显示原因。
10. 画像故障不影响播放和既有平台同步。

## 11. 测试和上线评估

单元测试覆盖画像状态读写、默认关闭、清除、损坏文件恢复、标签均分、冷启动、切歌位置、DJ 阈值、标签降权和永久恢复。服务端测试覆盖画像 API、恢复终态持久化和“画像失败不影响播放上报”。前端测试覆盖三种画像状态、双开关同步、前五首保护、手动拖动保护、交互错误反馈及短理由显示。

上线后按同一用户启用前后的相同观察窗口比较，并只统计推荐模式实际介入的播放。主要指标是快速切歌率下降和主动收藏率增加；每次结果必须同时显示样本量，样本不足不宣称推荐效果提升。
